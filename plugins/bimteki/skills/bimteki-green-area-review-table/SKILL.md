# BIMTeki 綠化面積檢討表生成

在目前開啟的 BIMTeki 專案中，建立一份兩欄式「綠化面積檢討」表格樣板（A0-05 常見）。這張表把綠化基準（實設空地／法定空地）、綠化有困難面積、應綠化面積、實設綠化面積與最終檢討、以及喬木數量檢討，濃縮成一張速覽表。

本表與其他檢討表最大的不同有二：

1. **需先把關「本案是否須做綠化檢討」**：綠化檢討**只針對都市計畫內地區（有土管）或其他特殊檢討條例（宜居建築、綠建築等）規定的案子**。若本案位於**非都市計畫地區（非都市土地）且無特殊條例要求**，則**不需要綠化檢討**——此時直接向使用者說明「本案位於非都市計畫地區、無綠化檢討義務」，**不建表**。
2. **規定值來自本案的土管**：綠化的應綠化比率、綠化困難的認定範圍、喬木每單位面積株數等，**依本案「土地使用分區管制要點」（土管）的綠化部分規定而定，各土管略有差異**。因此建表前務必先閱讀此案的土管，據以判斷各列的基準與算式；BIMTeki 端多已把這些參數設在專案裡（綠化參數 → 綠化類 autotext 的複合算式已算好），土管閱讀主要用來**確認基準與比率、並在專案未設參數時提醒使用者**。

左欄是固定的**項目標籤**，右欄「內容」依本案綁 `green` 分類 autotext。每一列的標籤、對應的 autotext 比對關鍵字、條件顯示邏輯與算式組法，**以 `references/items.md` 為準**；本檔描述整體流程。

> 需求前提：本 skill 需連上使用者本機的 Archicad + BIMTeki Studio 才能實際執行（MCP 工具會操作本機專案）。

## 前置檢查

1. 呼叫 `bimteki:check_connection` 確認與 Archicad / BIMTeki Studio 的連線。多開時先 `bimteki:list_archicad_instances` 讓使用者確認要操作哪個專案，再 `bimteki:set_active_archicad_instance` 選定。
2. 呼叫 `bimteki:get_project_status`（唯讀、成本低）確認專案狀態：`finalized` 為真代表案件已定案（本 skill 只建樣板、不寫專案資訊，仍應告知使用者）；`project_file.hasFile` 為假代表專案只在記憶體中、變更無法落地，請使用者先「另存新檔」。若回報未開啟 BIMTeki 專案，詢問使用者專案路徑後，用 `bimteki:open_bimteki_project` 協助開啟，再重試。
3. 動手前先讓使用者知道即將建立的樣板名稱（預設「綠化面積檢討」），這是寫入專案並存檔的操作。若使用者在 Archicad 開著表格編輯器等模態視窗，MCP 會回報 modal dialog 錯誤——請他關掉再繼續。

## 第一步：把關「本案是否須做綠化檢討」（做不做這張表）

呼叫 `bimteki:get_project_core_snapshot`，讀取本案的**使用分區／都市計畫**資訊，判斷是否位於都市計畫內地區：

- **位於都市計畫內地區（有土管）**：如使用分區為住宅區、商業區、工業區等都市計畫分區，且有對應都市計畫名稱／細部計畫。→ **須做綠化檢討，繼續下一步。**
- **位於非都市計畫地區（非都市土地）**：如甲／乙／丙／丁種建築用地、一般農業區、山坡地保育區等非都市土地分區，且無土管綠化規定、也無其他特殊條例（宜居建築、綠建築等）要求。→ **不須做綠化檢討。** 直接向使用者說明「本案位於非都市計畫地區、無土管綠化規定，依規定不需綠化面積檢討」，**不建表**，結束流程（除非使用者表示本案另有特殊條例要求綠化，才續作）。
- **判讀不明確時，不要臆測**：直接問使用者「本案是否位於都市計畫內地區、是否須依土管（或其他條例）做綠化檢討」，得到確認再決定做不做。

> 注意：即使位於都市計畫內，也可能該分區的土管未規定綠化義務；反之非都市土地也可能因宜居／綠建築等特殊條例而需綠化。**最終以土管（或適用條例）的綠化條文為準**——這正是下一步要讀土管的原因。

## 第二步：閱讀本案土管的綠化規定

**建表前務必先閱讀此案的土管**（土地使用分區管制要點），取得綠化部分的規定值。土管通常在專案資料夾內，或請使用者提供（PDF）。從土管綠化條文萃取：

- **綠化基準面積**：綠化率是以「**實設空地**」還是「**法定空地**」為基準（各土管用詞不同，直接影響第 2 列標籤與應綠化面積算式的分母）。
- **應綠化比率**：如「空地應留設 ◯◯% 以上綠化」。
- **綠化有困難面積的認定**：哪些部位（如車道、無頂蓋停車空間、必要設施）得計入「綠化有困難面積」而自基準扣除。
- **喬木數量規定**：如「每 ◯◯ 平方公尺綠地至少植喬木一株」。

> 臺灣政府機關的土管 PDF 文字層常為亂碼，若程式抽取出現大量亂碼，改用視覺方式逐頁閱讀（Read 工具會把 PDF 頁面渲染成影像）。條文為法規文字，抄錄正確性優先於速度。若專案已把綠化參數（應綠化比率、喬木密度等，見 `bimteki-lawname-index` 綠化面積索引 121~125）設好，`green` 分類的複合算式 token 已依這些參數算好，土管閱讀主要用來**核對基準與比率是否一致**；若讀到土管規定與專案設定不一致，回報提醒使用者，不要自行改動。

## 第三步：讀專案的綠化參數與計算結果（`get_project_green_info`）

呼叫 `bimteki:get_project_green_info`（唯讀），一次拿到本表需要的全部事實，**不要靠掃 catalog 猜**：

- `settings`：`base_type`（`"true_empty"`=實設空地／`"law_empty"`=法定空地，**直接決定第 2 列的標籤與應綠化面積的分母**）、`green_percentage`（應綠化比率）、`tree_unit`（每滿多少 m² 植喬木一株）、`tree_count`（實設喬木數量）、`area_source`。
- `areas`：`green_area`（設計綠化）、`unable_green_area`（無法綠化）、`custom_area_1~3`、`empty_area`（空地面積）、`should_green_area`（應設綠化面積），各含 `value`／`text`／`formula`。
- `review`：`green` 與 `tree` 兩組檢討式與 `isOk`。

**與土管對照**：把 `settings` 的比率與喬木密度跟上一步讀到的土管條文比對。

- 一致 → 直接進下一步。
- 不一致或專案尚未設定（例如比率是 0）→ **回報差異並詢問使用者是否要寫回**。使用者同意才呼叫 `bimteki:set_project_green_info`（可寫的只有 `base_type`／`green_percentage`／`tree_unit`／`tree_count`／`area_source` 這五項），寫入後會觸發重算，再重讀一次確認。**未經使用者同意不要自行改動專案設定。**
- 各項面積與兩個檢討式都是由綠化區域＋這些設定推導出來的，**不可寫入**；要改請改綠化區域。

## 取得綠化自動文字目錄並比對

呼叫 `bimteki:get_project_autotext_catalog(category="green")`（綠化相關分類，涵蓋本表絕大多數欄位）。掃描回傳項目的 `display` 名稱，依 `references/items.md`「自動文字對應」逐列比對取 `token`：

- **找到單一數值 token**（如「面積：實設空地」「面積：無法綠化面積」「面積：設計綠化面積」）→ 該處用 autotext segment。
- **找到複合「算式：／計算式：」token**（如「算式：應設綠化面積」「算式：綠化面積檢討式」「算式：喬木檢討式」，本身已含公式＋結果，且已依專案綠化參數算好）→ 整格只用這一個 token，不要再手動拼公式或寫死比率。
- **只有分開的數值 token** → 用文字運算符號（`×`／`－`／`＝`／`≧`）串接多個數值 autotext 自組，但每個數值都必須是 autotext，比率若無 token 才用土管讀到的比率當文字常數（並在回報標明來源）。
- **完全找不到** → 依項目性質退回佔位符或標準句，並在回報時標明。

**Token 是專案特定的雜湊值，絕對不要憑記憶或從其他專案硬編碼**；一律以 catalog 回傳的 display 比對後取用 token。`references/items.md` 的「顯示名稱候選」只是搜尋線索，實際專案 catalog 回傳名稱可能略有出入，找不到就依規則退回下一優先序，不要臆測硬湊。

## 判斷「綠化有困難面積」列是否顯示（條件顯示）

值直接取第三步 `get_project_green_info` 的 `areas.unable_green_area.value`，**不需要再另外求值**。若因故沒讀到，改呼叫 `bimteki:evaluate_autotext_values(category="green", displays=["面積：無法綠化面積"])`。

> **不要用 `evaluate_story_autotext_values`**：它只涵蓋 `storyArea` 一個分類，拿它評 `green` 分類的欄位會回空（而且不會報錯，容易被誤判成 0）。非 storyArea 的欄位一律用通用版 `evaluate_autotext_values(category=...)`；綠化欄位屬全案唯一值，不需要帶 story 脈絡。

- **綠化有困難面積 > 0**（`abs(value) >= 0.005`）→ 顯示該列。
- **= 0（本案無綠化困難部位）** → 該列可略過（應綠化面積直接等於基準×比率）；是否保留一列 `0` 由使用者決定，預設略過。
- 若兩條路徑都取不到值，不要臆測：保留該列並在回報說明「因數值取得失敗，未依 0 值判斷，請使用者複核」。

標題、基準面積（實設空地／法定空地）、綠化面積、應綠化面積、喬木數量檢討為**固定列，一律顯示**。

## 逐列組內容

依 `references/items.md`，依本案土管格式組出 1 列標題 + 各內容列（順序：實設空地／法定空地 → 綠化面積 → 綠化有困難面積 →〔條件〕 應綠化面積 → 喬木數量檢討，與使用者提供的土管格式一致；實際標籤與順序以本案土管為準）。每列：

- **左欄（col 0）**：項目標籤，用本案土管的用詞（如基準是法定空地就寫「法定空地面積」、是實設空地就寫「實設空地面積」）。
- **右欄（col 1）**：依上一節優先序組出 segments，`newline: 1`（直接換行）。內容較多的列（如應綠化面積、綠化面積檢討）可用「標籤＋`\t`＋autotext」逐行呈現，方便對齊閱讀。

## 建表流程

沿用 BIMTeki 兩欄表的已知眉角：

1. **組 cells**：
   - Row 0（標題）：col 0 放「綠化面積檢討」，`textbold: true`、`textsize: 1`、`alignment: 1`（靠左）、`newline: 1`；col 1 留空佔位（標題於 modify 階段跨欄合併）。
   - 其後各列：col 0 標籤與 col 1 內容皆 `alignment: 1`（靠左）、`newline: 1`。
2. 呼叫 `bimteki:create_project_table_template`，**一次把內容與版面帶齊**（v0.7.1 起 create 已支援 `merges` / `equal_col` / `right_line` / `bottom_line` / `left_line` / `top_line`，不必再「先建空表再 modify 補」）：
   - `cells`：全部儲存格。
   - `merges=[{"row":0,"col":0,"rowspan":1,"colspan":2}]`（標題跨兩欄、靠左）。**合併只能靠這個參數**——寫在 cell 上的 `rowspan`/`colspan` 建立時仍會被忽略。
   - `equal_col=[0,0]`：解除欄等寬。新建表格預設會把各欄設成強制等寬（讀回是 `equalCol=[0,1]`），使長算式的內容欄無法變寬；傳退化區間 `[0,0]`（等寬群組只含第 0 欄、放開第 1 欄）即可讓內容欄依內容加寬。
   - create 對未指定 `newline`/`charwidth` 的格，`charwidth` **預設為 1（縮減字寬）**；因此每一格都要明確給 `newline`，否則內容格會被非預期縮減字寬。
   - 取回傳 `nodeGuid`。
3. 呼叫 `bimteki:modify_project_table_template` 補上 create 收不到的樣板層級屬性：
   - `template_name`：預設「綠化面積檢討」；若同名樣板已存在，加日期後綴避免混淆。
   - `column_widths`：長度 2，起始 `[240, 660]`（項目欄窄、內容欄寬）。放置後欄寬仍不理想再與使用者確認微調。
   - `table_type="normal"`。
   - **若步驟 4 讀回發現 create 沒吃到 `equal_col`（讀回仍是 `[0,1]`）**，在此補傳 `equal_col=[0,0]`。舊版實測「傳 `equal_col=[]`（空陣列）不會生效」——一律用非空的退化區間 `[0,0]`，不要傳空陣列。
   - 若 create 階段有格式沒生效，一併在此以 `cells` patch 修正（只帶 row/col 與要改的格式欄位）。
   - **團隊協作要注意**：modify 前會比照樣板表格管理器，先整批保留所有已放置的表格；若有表格被其他使用者保留，會回傳錯誤與 `lockedTables`（每筆含 templateName／windowTitle／owner）**且不做任何修改**。此時把清單轉告使用者，請持有者釋放表格後再重試，不要反覆重送。
4. **驗證**：用 `bimteki:get_project_table_templates(template_guid=新guid)` 讀回，逐項核對：
   - 列數＝標題 1 列 + 固定內容列（實設空地／法定空地、綠化面積、應綠化面積、喬木數量檢討）+ 綠化有困難面積列（若判定顯示）。
   - 左欄標籤文字與本案土管用詞一致、順序正確。
   - 右欄該綁 autotext 的格含正確 token；複合「算式：」token 只出現一次、未被拆成多段；比率未被寫死成數字。
   - `merges`（標題）、`column_widths`、`equalCol`（應為 `[0,0]`，不是 `[0,1]`）符合預期。
   - **已知現象**：剛建立的樣板 `statedata` 顯示原始 token 字串是尚未評估的正常狀態，放到圖面後才解析成實際值；核對以 `originaldata` 是否含正確 token 為準。
5. **回報**：向使用者簡短說明——樣板名稱、本案判定為「須／不須」綠化檢討的依據（都計內／非都計）、採用的土管綠化規定（基準是實設空地或法定空地、應綠化比率、喬木密度）與來源、綠化有困難面積列是否顯示（及判斷結果）、各列綁到哪些 autotext（哪些綁到複合算式 token）、以及提醒可在 BIMTeki 表格管理器放置到圖面。若都計判定或土管規定是問使用者才確定的，回報時再次點明本次採用的假設。

## 儲存格寫法

- **固定標籤**：`{"row": 1, "col": 0, "text": "法定空地面積", "newline": 1}`（標籤用本案土管用詞）。
- **單一數值 autotext**：
  ```json
  {"row": 1, "col": 1, "newline": 1,
   "segments": [{"type": "autotext", "token": "${...面積：法定空地...}"}]}
  ```
- **複合算式 token（優先，公式與結果都在同一個 token 裡，已依綠化參數算好）**：
  ```json
  {"row": 4, "col": 1, "newline": 1,
   "segments": [{"type": "autotext", "token": "${...算式：應設綠化面積...}"}]}
  ```
- **無複合 token 時自組算式**（操作數皆為 autotext，運算符與等號為純文字；比率無 token 才用土管讀到的常數）：
  ```json
  {"row": 4, "col": 1, "newline": 1,
   "segments": [
     {"type": "autotext", "token": "${...面積：法定空地...}"},
     {"type": "text", "value": "－"},
     {"type": "autotext", "token": "${...面積：無法綠化面積...}"},
     {"type": "text", "value": "）×50％＝"},
     {"type": "autotext", "token": "${...面積：應設綠化面積...}"}
   ]}
  ```
  若「結果」也找不到 token，最後一段改成文字佔位符 `（請依左式計算後填入）`，不要自行算出數字。
- **綠化面積檢討（實設≧應綠化 結論）＋喬木數量逐行呈現**（沿用土管檢討表的逐行寫法）：
  ```json
  {"row": 5, "col": 1, "newline": 1, "alignment": 1,
   "segments": [
     {"type": "text", "value": "應綠化面積\t"},
     {"type": "autotext", "token": "${...算式：應設綠化面積...}"},
     {"type": "text", "value": "\n實設綠化面積\t"},
     {"type": "autotext", "token": "${...面積：設計綠化面積...}"},
     {"type": "text", "value": "\n檢討\t"},
     {"type": "autotext", "token": "${...算式：綠化面積檢討式...}"},
     {"type": "text", "value": "\n喬木數量\t"},
     {"type": "autotext", "token": "${...算式：喬木檢討式...}"}
   ]}
  ```
  **已知限制**：儲存格只能整格套用粗體，無法只加粗其中一行；若使用者要強調「檢討」那行，需到 Archicad 內手動調整。
- **格式欄位**：`textbold`(粗體，僅標題)、`textsize`(1 大，僅標題／2 一般)、`alignment`(1 靠左／2 置中，僅標題)、`newline`(0 不換行／1 直接換行／2 依中文換行)。本表每格都明確給 `newline` 以避免預設縮減字寬。
- 本表所有內容皆屬專案層級 autotext，儲存格不需帶 `storyGuid`。

## 注意事項

- **先把關再建表**：綠化檢討只對都市計畫內（有土管）或特殊條例規定的案子做；非都市計畫地區且無特殊條例要求時**不建表**，直接說明免檢討，不要為了交差硬生成一張空表。
- **規定值來自土管、不要憑記憶**：應綠化比率、綠化困難認定、喬木密度各土管不同；務必以本案土管為準。BIMTeki 的複合「算式：」token 已依專案綠化參數算好，優先整格綁定；即使當下能讀到數字算出結果，也不要寫死比率或面積。
- **算式優先找複合 token，其次自組，絕不手算寫死**：與 `bimteki-coverage-review-table` 同原則。
- **不可捏造**：都計判定讀不到時問使用者，不要臆測；土管規定與專案的綠化設定不一致時**回報差異、詢問後才用 `set_project_green_info` 寫回**，不要自行改動；任何外部或行政資訊留佔位符。
- 新建樣板會寫入專案並存檔，屬可逆性低操作；刪除舊樣板（`manage_project_table_templates` 的 delete）必須先取得使用者明確同意。
- 一次組好完整 cells 再送出 create，不要分多次產生殘缺樣板；create 失敗，修正後重試前先確認沒有留下半成品樣板。
