# 各層樓地板面積 — 表格結構規格（依案型動態組表）

本規格支援：（單棟／一般多棟）× 共用梯廳／非共用梯廳，共 4 種，**加上**連棟透天多棟（此案型
不分共用/非共用梯廳，固定視為非共用梯廳處理）1 種，合計 5 種案型組合。欄位**都是動態的**：先由
「標準欄位清單」出發，依案型與各空間項目是否為 0 過濾掉欄位，再**依序重新編號**成實際 col 索引，
最後依實際欄數組出表頭合併、檢討列與最終列的 colspan。樓層列的**來源**則依單棟／一般多棟／連棟
透天三種案型分別決定（見四之 2）。

除非使用者提供了自己的範例表格檔案，一律照此規格生成。

## 一、案型判斷（來源：get_project_core_snapshot 的 building 區塊）

- `shared_hall.value`：`true` = 共用梯廳、`false` = 非共用梯廳。**連棟透天案型不適用此概念**
  （各棟本來就各自獨立出入口，沒有共用梯廳），判斷為連棟透天後直接視為非共用梯廳處理，不需再讀
  `shared_hall.value`。
- `block_mode.value`：`true` = 多棟、`false` = 單棟。
- `block_count.value`：棟數（多棟時 ≥ 2，供回報參考）。
- `case_type.is_row_house`（或 `case_type.value == "row_house"`）：`true` = 連棟透天（分棟檢討）。
  只在 `block_mode.value == true` 時有意義；`block_mode.value == false`（單棟）時忽略此欄位。
  若專案回傳的 `building` 區塊沒有 `case_type` 欄位，見 SKILL.md「判斷案型」一節的保險判斷法。

## 二、標準欄位清單（依序，未過濾）

每欄屬性：`group`（fixed／B／C）、`sub`（第 3 列子欄表頭文字，fixed 欄無）、`display`
（storyArea 分類中對應的 autotext display 名稱，用來取 token 綁值）、`space`（是否為「空間項目」＝
可因專案該項為 0 而移除）、`sharedOnly`（是否僅共用梯廳顯示）。

**連棟透天專屬的「棟別」欄**：連棟透天多棟案型固定在標準欄位清單**最前面**多一欄「棟別」，
不受任何過濾規則影響（不是 `space`，不受 0 值過濾；不是 `sharedOnly`）。單棟與一般多棟案型
**不要**加這一欄。加了這欄之後，原本清單中「層別」以下所有欄位的最終 col 索引都要整體 +1；
下表仍以「不含棟別欄」的原始序號描述，實際組表時依「四之 0」規則統一位移。

## 三、欄位過濾（決定最終要保留哪些欄）

依序套用兩道過濾，順序不可顛倒：

1. **非共用梯廳過濾**：若 `shared_hall.value == false`**或案型為連棟透天**（連棟透天固定視為
   非共用梯廳，不管 `shared_hall.value` 實際回傳什麼），移除所有 `sharedOnly == 是` 的欄
   （梯廳面積、陽台10%回計、梯廳10%回計、陽台+梯廳15%回計 共 4 欄）。一般案型且共用梯廳則全留。

2. **0 值空間欄過濾**：對「全案總計樓層」取每一個 `space == 是` 欄位的解析後數值，數值為 0
   （建議容差 `abs(value) < 0.005` 視為 0）者移除該欄。`space == 否` 的固定欄
   （層別、樓高、A、D、用途）一律保留，不受此過濾影響。
   - 取值來源見「六、取得解析後數值」。全案總計樓層 guid 的選法見「五、樓層列與總計列」。
   - 邊界：若某群組（B 或 C）過濾後 0 欄存活，則該群組表頭整段省略；實務上 B 群幾乎必有存活欄。

過濾後，把剩餘欄位**依原順序重新編號**為 0-based 的實際 col 索引。**連棟透天多棟案型**編號前，
先在最前面插入「棟別」欄佔掉 col 0，其餘欄位依序往後排（即「層別」變成 col 1、原本 col 0 的
欄位全部 +1）；單棟與一般多棟不做此插入，「層別」維持 col 0。以下所有 row/col、colspan、
merges、column_widths 一律以「（若連棟透天則已插入棟別欄後）重新編號後的實際索引」為準。設：
- `N` = 最終欄數（連棟透天案型含棟別欄；即一般情況欄數 +1）；最後一欄索引 = `N-1`（必為「用途」）。
- `Dcol` = 「D」欄的最終索引（連棟透天案型已包含棟別欄造成的位移）。
- `firstB` / `countB` = B 群存活欄的首索引與欄數；`firstC` / `countC` = C 群同義（同樣已含位移）。
- 為方便描述，下文仍以「層別＝col 0」表示非連棟透天情況；連棟透天時請將所有 col 索引整體 +1，
  並在最前面多出的 col 0 放「棟別」欄（內容規則見四之 2 連棟透天段落，標頭規則見四之 1）。

## 四、列配置

由上而下：大標題(1) → 群組表頭(1) → 子欄表頭(1) → 樓層列(動態) → 總計列(1) →
機電空間容積檢討列(0~1，依條件) → 地下層容積檢討列(0~1，依條件) → 最終容積樓地板面積列(1)。
兩列檢討的顯示條件見四之 4；兩列都不顯示時，總計列後直接接最終容積樓地板面積列。

### 1. 標題（3 列，textbold: true）

**大標題（row 0）**：(0,0) text「各　層　樓　地　板　面　積」，alignment 2，textsize 1，
合併 colspan `N`。

**群組表頭（row 1）**，textsize 2、有字的格 charwidth 1：
- **連棟透天多棟**：(1, 0)「棟　別」rowspan 2，alignment 2（此欄只在連棟透天案型出現；單棟與
  一般多棟沒有這一列）。
- (1, 「層別」col)「項　目\n層　別」rowspan 2，alignment 1。（非連棟透天為 col 0；連棟透天為 col 1）
- (1, 「樓高」col)「樓　高」rowspan 2，alignment 2。（非連棟透天為 col 1；連棟透天為 col 2）
- (1, 「A」col)「樓地板面積(A)」rowspan 2，alignment 2。（非連棟透天為 col 2；連棟透天為 col 3）
- 若 `countB > 0`：(1, firstB)「不計入容積樓地板面積(B)」colspan `countB`，alignment 2。
- 若 `countC > 0`：(1, firstC)「計入容積樓地板面積(C)」colspan `countC`，alignment 2。
- (1, Dcol)「容積樓地板面積(D)」alignment 2（不與 row 2 合併）。
- (1, 陽台面積 col)「陽台面積」rowspan 2，alignment 2。（若該欄被 0 值過濾掉則不出現）
- (1, N-1)「用　途」rowspan 2，alignment 2。

**子欄表頭（row 2）**，textsize 2、有字的格 charwidth 1、alignment 2：
- 對每個存活的 B 欄與 C 欄：(2, 該欄 col) 放其 `sub` 文字。
- (2, Dcol)「D = A-B+C」。
- 棟別／層別／樓高／A／陽台面積／用途 因 rowspan 2，不放 row 2。

### 2. 樓層列（依 storyGuidList 動態；storyArea 分類，textbold: false，textsize 2）

先依案型決定「要當成樓層列的 storyGuidList 項目」：

- **單棟（block_mode.value == false）**：取 storyGuidList 中**除名稱恰為「總計：」以外**的所有項目，
  依清單順序排列。每列各格帶「該項目自己的 storyGuid」。（含夾層小計等 `小計` 列一律保留。）
- **一般多棟（block_mode.value == true 且 case_type.is_row_house 不為 true）**：只取名稱
  **以「各棟總計」開頭**的項目（例如「各棟總計地上一層」「各棟總計地上七層小計」），依清單順序
  排列，各格帶該項目 guid。不要用各棟自身樓層（A棟…／B棟…）當列，也不要用任何「總計：」列當
  樓層列。**注意**：像「各棟總計地上七層小計」這種小計列是**夾層**造成、必須保留（並非因多棟而
  生的合計）。
- **連棟透天多棟（block_mode.value == true 且 case_type.is_row_house == true）**：此案型的
  storyGuidList **沒有**「各棟總計」節點，只有「各棟各自樓層 →（該棟）總計： → 下一棟各自樓層 →
  （該棟）總計： → … → 全案總計：」的排列方式。**此案型固定內建「棟別」欄（col 0，見四之 1）**，
  固定用以下結構組樓層列（不詢問使用者是否要跨棟合併同層，因為底層資料本來就不支援跨棟合計）：
  1. 依棟別分段，每段依序列出該棟的所有樓層（含夾層），每列帶該樓層自己的 storyGuid。
  2. 每一棟樓層段結束後，緊接一列「該棟小計」：col「層別」（非連棟透天為 col 0，連棟透天為 col 1）
     用**固定文字**（非 autotext）標示「Ｘ棟小計」，其餘存活欄（不含 col 0 棟別欄）用 autotext
     綁定「該棟在 storyGuidList 中對應的『總計：』節點」guid，textbold 設為 true。
  3. 所有棟別段落跑完後，最後加一列「全案總計」：col「層別」固定文字「總　計」（比照一般案型
     總計列寫法），其餘存活欄（不含 col 0 棟別欄）用 autotext 綁定 storyGuidList 中**最後一個**
     「總計：」節點 guid，textbold 設為 true。此列即取代四之 3 所述的「總計列」，兩者不要重複
     出現。col 0（棟別欄）留空、不合併。
  4. **棟別欄（col 0）內容**：對每一棟的樓層段（含該段結尾的小計列，共「該棟樓層數＋1」列），
     用一個**垂直合併儲存格**（rowspan＝該棟樓層數＋1，colspan 1）呈現，只在合併範圍最上面一列
     的 col 0 放內容，其餘列的 col 0 不建立儲存格（由合併吸收）。內容為**固定文字**「Ｘ棟」，
     alignment 2（置中），textbold true，charwidth 1；`Ｘ` 為該棟代號，判斷方式：取
     storyGuidList 中該樓層段第一筆樓層名稱裡「棟」字前面緊鄰的字元（例如「A棟地上一層」→取
     「A」），若為半形英文字母則轉換成全形（A→Ａ、B→Ｂ…），與「Ｘ棟小計」標籤的棟別代號用同一套
     判斷法、確保一致。全案總計列（步驟 3）的 col 0 不併入任何棟別合併範圍，留空但仍要放一個空白
     儲存格（`text: ""`），避免遺漏儲存格造成表格結構跳號。
  5. 判斷「storyGuidList 中每個『總計：』節點屬於哪一棟」：以該「總計：」節點在清單中的位置為準，
     它是「該棟樓層段結束後、下一棟樓層段開始前」出現的第一個「總計：」；不要用名稱字串比對（因為
     不同棟的小計節點名稱可能相同，都是「總計：」）。

**騎樓列（條件顯示，所有案型皆適用）**：本案有騎樓時，**在「地上一層」那一列之前插入一列騎樓列**
（即樓層列的最前面），呈現騎樓的樓地板面積。判斷與寫法：

- **顯示條件**：本案騎樓樓地板面積 > 0。判斷用 `evaluate_autotext_values(category="buildingOverview",
  displays=["面積：騎樓總樓地板面積"])`（專案層級、全案唯一值，`abs(value) < 0.005` 視為 0 → 不插入本列）。
  **不要用 storyArea 的「面積：騎樓」逐層判斷**——騎樓常被建成「建築面積」區域而非容積區域，逐層值
  會是 0，據以判斷會誤判為無騎樓（見下方「已知落差」）。
- **col「層別」**：固定文字 `騎樓`（非 autotext），alignment 1、charwidth 1。
- **col「樓地板面積(A)」**：綁**騎樓**的自動文字，alignment 2、charwidth 0。
  - 首選 storyArea 的 `面積：騎樓`（story 相依），並在該格帶 **`storyGuid` ＝「地上一層」**的 guid
    ——騎樓在請照上歸屬地面層，樓層屬性設為地上一層。
  - **已知落差**：若該案的騎樓是以「建築面積」區域（請照空間名稱常顯示為「騎樓\*」）建模、而非容積
    區域，storyArea 的騎樓逐層值會解析為 0。此時改綁 buildingOverview 的 `面積：騎樓總樓地板面積`
    （專案層級，不需 storyGuid，仍把該格的 storyGuid 設為地上一層以維持樓層脈絡一致）。
    **建表前先用 `evaluate_autotext_values` 對地上一層解析 storyArea 的「面積：騎樓」確認**：非 0
    就用 story 相依版，為 0 但專案層級騎樓面積 > 0 就用專案層級版，並在回報中說明改綁原因。
- **col「樓高」**：留空（`text: ""`）。
- **col「用途」（col N-1）**：本案騎樓的實際用途文字（例如 `人行道`），`newline: 2`；讀不到就留空，不要臆測。
  本列其餘各格一律 `newline: 0`（見第八節換行通則）。
- **其餘存活欄（B 群、C 群、D、陽台面積）**：留空（`text: ""`）——騎樓不計入容積，不要綁 token
  讓這些格顯示 0。
- 插入本列後，其後所有樓層列、總計列、檢討列、最終列的 row 索引一律 +1，`merges` 也要跟著平移。

**小計列重排**（單棟、一般多棟皆適用；連棟透天已在上方步驟中內建棟別小計順序，不需要再套用本段
的小計重排規則）：storyGuidList 常把「…XX層小計」排在整段最後，位置不對。取得樓層列清單後，對
每一個名稱**以「小計」結尾**的列，將它從原位置移出，插入到「其名稱去掉結尾『小計』後的字串」所
匹配之**最後一個**樓層列之後（涵蓋該層與其夾層）。例如「各棟總計地上七層小計」→ 基底「各棟總計
地上七層」→ 匹配「各棟總計地上七層」「各棟總計地上七層夾層」，故插到「各棟總計地上七層夾層」之
後。其餘樓層列相對順序不變。

每個樓層列的儲存格：
- **連棟透天多棟**：col 0 是棟別欄，規則見上方步驟 4（垂直合併＋固定文字），不使用 autotext。
- col「層別」（非連棟透天 col 0，連棟透天 col 1）：`層別` 的 display（樓層名稱）token，
  alignment 1，charwidth 1。（連棟透天的「棟別小計」與「全案總計」列例外：此欄用固定文字，
  不用 autotext，見上方連棟透天段落與四之 3。）
- col「樓高」（非連棟透天 col 1，連棟透天 col 2）：`樓高` 的 display token，alignment 2，
  charwidth 0，帶該樓層 storyGuid。**聚合類節點不會合計樓高、一律解析為 0**（實測「總計：」
  isSumStory 虛擬樓層與「XX層小計」夾層小計節點皆回 0）：凡名稱以「小計」結尾的樓層列（含
  夾層小計）、連棟透天的「棟別小計」列與「全案總計」列，此欄一律留空（`text: ""`），不要綁
  token 讓表面顯示 0。
  **一般多棟注意**：一般多棟的樓層列本身綁的是「各棟總計XX層」聚合節點，樓高很可能也解析為 0
  （依聚合節點行為推定，尚未以實案驗證；且跨棟同層樓高本可不同，本無單一正確值）；組表前先用
  `evaluate_story_autotext_values` 對「各棟總計」各層解析 `樓高`，全為 0 或 null 時**整欄移除
  樓高欄**（比照 0 值空間欄重新編號）並在回報中說明原因；能解析出合理值才保留並正常綁定。
- 中間各存活欄（A、B 群、C 群、D、陽台面積）：對應 `display` 的面積 token，alignment 2，charwidth 0。
- col N-1（用途）：`用途` token，alignment 1，charwidth 0，**newline: 2（依中文換行）**。一般樓層列
  才有用途欄內容；連棟透天的棟別小計列與全案總計列比照一般案型總計列，用途欄留空。
- 每格都要帶該樓層（或該小計/總計節點）的 `storyGuid`；固定文字格不需要 storyGuid。

### 3. 總計列（1 列，textbold: true）

- 全案總計樓層 guid 選法：
  - 單棟：storyGuidList 中名稱為「總計：」的那一項（僅一個）。
  - 一般多棟：storyGuidList 中**最後一個**名稱為「總計：」的項目（＝各棟總計段之後的全案合計）。
  - 連棟透天多棟：**不要在這裡另外組總計列**——全案總計列已在四之 2「連棟透天多棟」步驟 3 中，
    作為樓層列清單的最後一列產生，避免重複兩列總計。
- **非連棟透天**：col 0：text「總　計」，alignment 1，charwidth 1（不帶 storyGuid）。
- **連棟透天多棟**：col 0（棟別欄）與 col 1（層別欄）**固定合併成一格**（colspan 2），內容
  text「總　計」放在 col 0，col 1 明確送一個空字串 `text: ""`（避免殘留舊內容或跳號），不要
  省略 col 1 的儲存格。
- 樓高欄：**留空**（`text: ""`）。實測「總計：」虛擬樓層不會合計樓高（解析回 0），綁 token 只會
  顯示 0；若日後版本能解析出合理的高度合計再改綁。
- **col「樓地板面積(A)」：不要用樓層列那個 `面積：當層樓地板面積`**（它只合計各層當層面積、**不含
  騎樓**，與本表的騎樓列相加後會對不起來）。改綁 **buildingOverview 的 `計算式：總樓地板面積`**
  （專案層級複合算式 token，本身即輸出如 `236.76+14.34(騎樓) = 251.10m²`，公式與結果一次到位），
  **不需帶 storyGuid**，alignment 2。
  - 找不到該 display 時，退回同分類的 `面積：總樓地板面積`（純數值）；兩者都找不到才退回
    `面積：當層樓地板面積`＋全案總計 guid，並在回報中說明總計不含騎樓。
- 中間其餘存活欄（B 群、C 群、D、陽台面積）：與樓層列相同的 `display` token，但 `storyGuid` 一律用
  上面選出的全案總計 guid，alignment 2。
- col N-1（用途）：空。

### 4. 檢討列（0～2 列，textbold: false，token 取自 volumeCheck / startmanager，不需 storyGuid）

  重複呼叫。若「機電設備」欄已因 0 值被過濾移除，本列必省略。若 `evaluate_story_autotext_values`
  不可用（0 值過濾被跳過的情況），本列照舊保留，並在回報中說明未套用此判斷。
- **地下層容積檢討列**：僅當**同時**滿足以下兩條件才顯示：
  1. 專案採**地下層總量檢討**：`get_project_core_snapshot` 的

## 五、樓層列與總計列（storyGuidList 判讀重點整理）

**一般多棟** storyGuidList 的典型排列：
`A棟各層… →「總計：」→ B棟各層… →「總計：」→ 各棟總計各層… →「總計：」`。
因此：樓層列＝「各棟總計」開頭者；總計列＝最後一個「總計：」。

**連棟透天多棟** storyGuidList 的典型排列（**沒有**「各棟總計」段）：
`A棟各層… →「總計：」(A棟小計) → B棟各層… →「總計：」(B棟小計) → …
（可能還有「A棟」「B棟」等 guid 與前面小計節點重複的項目，忽略即可）→「總計：」(全案總計)`。
判讀時依「棟樓層段 → 該棟總計：」的相鄰順序抓出每棟小計，並取**最後一個**「總計：」為全案總計；
不要用名稱字串比對，因為每個「總計：」節點名稱都相同。

單棟則只有一段樓層加單一「總計：」。

## 六、取得解析後數值（0 值欄位判定用）

catalog 只給 token、不給數值；剛建立、未放置到圖面的樣板 `statedata` 也是未評估的原始 token。
因此 0 值欄位判定需呼叫 **`bimteki:evaluate_story_autotext_values`**（依樓層脈絡解析 storyArea
自動文字欄位值，唯讀、不開面板）：

> ⚠ 這個工具**只涵蓋 storyArea 一個分類**。本表的欄位（各空間面積、樓高、用途）都屬 storyArea，
> 用它正確；但檢討列用到的 volumeCheck token（允建機電設備空間計算式、地下室容積檢討式…）
> **不在它的範圍內**，需要求值時改用通用版 `bimteki:evaluate_autotext_values(category="volumeCheck")`。
> 用錯分類不會報錯、只會回空，很容易被誤判成 0。

- 輸入：`story_guids`（樓層 guid 陣列，至少含全案總計 guid；省略＝全部樓層）、
  `displays` 或 `tokens`（要解析的 storyArea 欄位，省略＝該分類全部）。
- 輸出：每筆 `{ storyGuid, storyName, isSumStory, display, token, value, text }`；`value` 為數值
  （算式欄取等號後結果，無法解析為 null）。各「總計：」虛擬樓層回傳 `isSumStory: true`。
- 判定：對全案總計 guid（見第五節，多棟取最後一個「總計：」）取各 `space == 是` 欄位的 `value`，
  `abs(value) < 0.005` 視為 0 → 移除該欄。建議一次帶齊所有 `space` 欄的 display 以省往返。
- 同一工具也可用來解析 `樓高` display 確認各樓層值正常；聚合類節點（「總計：」isSumStory 節點
  與「XX層小計」夾層小計節點）實測不會合計樓高、一律回 0，故小計列與總計列的樓高格固定留空；
  一般多棟的「各棟總計」樓層列也屬聚合節點，組表前應先以此工具確認樓高可否解析，不能就整欄移除
  （見四之 2、四之 3）。

**若此工具回錯或不可用**：不要臆測數值、也不要用區域圖資（get_bimteki_zone_map）硬湊
（其 permitSpaceName 與表格欄位並非一對一，例如「防空避難室」區域常被歸在「停車空間」而使該欄
總計為 0，且回計欄根本不是區域）。改為**跳過 0 值過濾、保留所有（非共用過濾後的）欄位**，
並在回報時明確告知使用者「因解析數值取得失敗，本次未自動移除 0 欄」。

## 七、表格層級屬性（用 modify_project_table_template 設定）

- `template_name`：「各層樓地板面積」（同名已存在可加日期後綴）。
- `equal_col`: `[0, N-1]` — 所有欄位同寬儲存格。
- `column_widths`: 長度 `N`，每欄 100，最後一欄（用途，索引 N-1）給 380。**連棟透天多棟**因多了
  棟別欄，col 0（棟別）建議給較窄的 60，其餘欄位規則不變（含棟別欄的下一欄「層別」仍給 100）。
- `table_type`: `"normal"`；不設樣板層級 story_guid / room_guid（樓層脈絡由各格 storyGuid 決定）。
- 框線：預設全 1。**若對既有樣板用 `insert_cols` 插入棟別欄**，有兩類已知風險都要檢查：
  1. 插入後新欄與其相鄰欄的框線（`right_line` 中新欄那一直行、`bottom_line`／`top_line` 對應位置）可能不會自動補齊，插入完成後務必用 `get_project_table_templates` 讀回 `leftLine`／`rightLine`／`topLine`／`bottomLine` 檢查是否有缺漏的 0，若有則用 `right_line`／`bottom_line`／`top_line` 補送整組陣列（1 = 有框線）修正。
  2. **合併儲存格（如大標題 row 0 的 colspan `N`）的內容會跟著原本錨點欄位一起位移，但合併設定本身的錨點 col 不會跟著調整**：插入前若合併錨點在 col 0（例如大標題），插入 1 欄後該儲存格內容會位移到新的 col 1，但 merges 清單裡的錨點仍是 col 0，導致合併範圍的左上角是空的、內容顯示不出來（大標題整個消失）。插入欄位後，只要有任何合併儲存格的原錨點是 col 0（或任何位移到的欄位），都要用 `cells` patch 把內容搬回新的 col 0，並把原本內容所在的欄位清成空字串 `text: ""`；不要只看 merges 有沒有正確，一定要連內容一起核對，讀回後確認 `originaldata` 真的出現在合併錨點那一格。

## 八、格式速查

> **換行規則（全表通則，優先於個別列的描述）**：**只有「用途」欄（col N-1）用 `newline: 2`（依中文換行）；
> 其餘所有儲存格一律 `newline: 0`（不換行）**——包含大標題、群組／子欄表頭、騎樓列、樓層列、總計列、
> 機電／地下層檢討列與最終容積樓地板面積列。檢討列與最終列的內容較長，但要靠合併欄寬容納，
> **不要靠自動換行**；需要斷行時用內容裡的手動 `\n`（例如表頭「項　目\n層　別」），那是結構性斷行、
> 與 `newline` 屬性無關。
> ⚠ `newline` 與 `charwidth: 1` 互斥：把 `newline` 設為 0 時，仍要**明確**給定該格的 `charwidth`
> （表頭與 col 0 標籤給 1、數值格給 0），否則會落到預設值而非你要的字寬。

| 需求 | 欄位 | 值 |
|----|----|----|
| 粗體（標題 3 列、總計列、最終列、檢討列 D 欄） | textbold | true |
| 縮減字寬（群組/子欄表頭有字的格、col 0 標籤與樓層名） | charwidth | 1 |
| 依中文換行（**只有用途欄**，自樓層列起） | newline | 2 |
| **不換行（用途欄以外的全部儲存格，含大標題、表頭、騎樓列、樓層列、總計列、檢討列、最終列）** | newline | **0** |
| 靠左（col 0、用途欄、檢討內容） | alignment | 1 |
| 置中（標題、表頭、數值欄） | alignment | 2 |
| 大標題字級（僅 row 0） | textsize | 1，其餘 2 |
